**M14 is genuinely possible.** But I would slightly change how I described it.

The browser will never allow Vita3K to do a conventional Dynarmic-style JIT:

```text
ARM code
   ↓
emit x86-64 machine code
   ↓
mmap(PROT_EXEC)
   ↓
jump to it
```

That part is impossible under the normal browser sandbox.

But this is allowed:

```text
ARM code
   ↓
Vita3K IR
   ↓
generate WebAssembly binary
   ↓
browser compiles that Wasm
   ↓
execute compiled function
```

`WebAssembly.compile()` / `WebAssembly.Module()` explicitly support creating executable Wasm modules from runtime-generated bytes. ([MDN Web Docs][1])

And, critically, separately instantiated Wasm modules can **share the same `WebAssembly.Memory` and `WebAssembly.Table`**. MDN specifically describes this as a mechanism for runtime dynamic linking. ([MDN Web Docs][2])

So the fundamental mechanism required by M14 exists today.

### What it could actually look like

Suppose P4G reaches:

```text
PC = 0x81001234
```

and there's no compiled translation.

The dispatcher initially does:

```cpp
CompiledBlock* block = cache.lookup(pc);

if (!block) {
    return ExitReason::CompileBlock;
}
```

The browser-side compilation service receives something approximately like:

```text
guest PC: 0x81001234

ARM:
    ldr r1, [r0, #4]
    add r2, r1, #1
    str r2, [r0, #4]
    cmp r2, #100
    blt 0x81001234
    bx lr
```

The translator produces a small Wasm module conceptually resembling:

```wat
(module
  (import "env" "memory" (memory ...))
  (import "env" "dispatch_table" (table ... funcref))

  (func $block_81001234 (param $state i32) (result i32)
      ;; translated ARM instructions
      ...
  )

  (export "block" (func $block_81001234))
)
```

It is compiled by the browser:

```js
const module =
    await WebAssembly.compile(generatedBytes);

const instance =
    await WebAssembly.instantiate(module, {
        env: {
            memory: vita3kMemory,
            dispatch_table: vita3kTable
        }
    });
```

and the resulting function gets installed into the dispatch structure.

The fact that two Wasm modules can use the same memory/table is not a hack; WebAssembly deliberately supports it. ([MDN Web Docs][2])

Emscripten itself uses essentially this shared-module model for its dynamic linking implementation: one main Wasm module and runtime-loaded side modules. ([Emscripten][3])

So:

> **Can runtime-generated ARM translations execute against Vita3K's existing Wasm heap?**

Yes.

## There is one correction to my original diagram

I previously made it look like:

```text
Vita3K.wasm
      ↓
generates Wasm
      ↓
WebAssembly.compile()
```

as though C++ could directly call the Wasm compiler.

That's not really what happens.

The browser's WebAssembly compilation API is a **host JavaScript API**. So the actual architecture would probably be:

```text
┌──────────────────────── Emulator Worker ──────────────────────┐
│                                                               │
│                Vita3K main Wasm instance                      │
│                                                               │
│ ARM dispatcher                                                │
│      │                                                        │
│      │ cache miss                                             │
│      ▼                                                        │
│ Browser JIT bridge                                            │
│      │                                                        │
│      ▼                                                        │
│ Generate Wasm binary                                          │
│      │                                                        │
│      ▼                                                        │
│ WebAssembly.compile()                                         │
│      │                                                        │
│      ▼                                                        │
│ New Wasm module                                               │
│      │                                                        │
│      ├──────── imports same Memory ────────────────┐          │
│      └──────── imports same Table ──────────────┐ │          │
│                                                 │ │          │
│                Vita3K.wasm ◄────────────────────┘ │          │
│                       ▲                           │          │
│                       └───────────────────────────┘          │
└───────────────────────────────────────────────────────────────┘
```

There therefore **is** a JS boundary when compiling new guest code.

There does **not** need to be one while executing every translated block.

That's the important distinction.

## In fact, I'd make compilation asynchronous

This is where it gets quite interesting.

`WebAssembly.Module` objects can be efficiently transferred/shared with Workers. ([MDN Web Docs][4])

So the architecture could eventually be:

```text
                   Emulator Worker
                         │
                    cache miss
                         │
                         ▼
                ARM → intermediate IR
                         │
             compilation request
                         │
                         ▼
                JIT Compiler Worker
                         │
                generate Wasm bytes
                         │
              WebAssembly.compile()
                         │
                         ▼
               WebAssembly.Module
                         │
                 postMessage()
                         │
                         ▼
                  Emulator Worker
                         │
                   instantiate
                         │
                         ▼
                 compiled cache
```

Meanwhile, execution could temporarily:

```text
interpret cold block
```

until compilation finishes.

So you'd have tiering:

```text
first execution
      ↓
 interpreter
      ↓
execution counter
      ↓
      hot?
       │
      yes
       ↓
queue compilation
       ↓
ARM → Wasm
       ↓
browser optimizer
       ↓
subsequent execution uses compiled version
```

That's substantially nicer than stopping the emulator every time a new ARM address is encountered.

# And ARM maps surprisingly well to Wasm

A lot of ARMv7 operations have straightforward mappings.

For example:

```asm
ADD r0, r1, r2
```

roughly:

```wat
local.get $r1
local.get $r2
i32.add
local.set $r0
```

Likewise:

```asm
AND r0, r1, r2
```

becomes:

```wat
local.get $r1
local.get $r2
i32.and
local.set $r0
```

Loads:

```asm
LDR r0, [r1, #8]
```

can become basically:

```wat
local.get $guest_memory_base
local.get $r1
i32.add
i32.const 8
i32.add
i32.load
local.set $r0
```

assuming we've designed Vita memory appropriately.

And Wasm has native:

```text
i32
i64
f32
f64

integer shifts
rotates
clz
popcnt
comparisons
SIMD128
atomics
```

which overlap nicely with a substantial portion of ARM/VFP/NEON operations.

Not everything is one instruction, obviously. ARM's flags and several NEON operations require extra lowering.

But we're not trying to emulate ARM with JavaScript arithmetic.

We're effectively asking the browser's JIT to perform:

```text
ARM semantics
   ↓
WebAssembly SSA-ish bytecode
   ↓
TurboFan / Cranelift / B3 etc.
   ↓
native machine code
```

which is quite attractive.

# Even block chaining can work

A naive implementation would continually do:

```text
Wasm translated block
       ↓
return to Vita3K dispatcher
       ↓
lookup PC
       ↓
call next Wasm block
       ↓
return
```

That would introduce unnecessary dispatch overhead.

Instead, translated regions can call through a shared WebAssembly table:

```wat
local.get $next_block_index
call_indirect
```

Wasm tables are explicitly intended to hold callable function references and support indirect calls. ([MDN Web Docs][2])

So eventually:

```text
ARM block A
    ↓
compiled Wasm A
    │
    │ call_indirect
    ▼
compiled Wasm B
    │
    │ call_indirect
    ▼
compiled Wasm C
```

can stay entirely in WebAssembly.

Only exceptional events need to return to the emulator:

```text
SVC
interrupt
thread switch
unmapped memory
code-cache miss
code invalidation
debug breakpoint
```

That's much closer to a real dynamic recompiler.

# We also don't necessarily need one module per block

And I **would not** do that.

Imagine P4G executing 500,000 unique basic blocks.

Creating:

```text
500,000 WebAssembly.Module objects
```

would probably be disastrous.

Instead I'd experiment with translation units such as:

```text
ARM function
     ↓
one Wasm function

~50–500 ARM functions
     ↓
one Wasm module
```

or hot regions:

```text
        81000000
          │
    ┌─────┴──────┐
    ▼            ▼
  block A       block D
    ↓             ↓
  block B       block E
    ↓
  block C

       ↓

compile entire discovered region

       ↓

one Wasm module
```

The ideal size is something we'd determine experimentally.

Too small:

```text
lots of compilation/module overhead
```

Too large:

```text
long compilation stalls
wasted compilation
difficult invalidation
```

There will probably be a sweet spot.

# Self-modifying code isn't fatal either

Suppose guest code changes:

```text
0x81001000–0x81002000
```

Vita3K marks that guest page as having translations:

```text
Guest page 0x81001
    ↓
Wasm module/regions
    ↓
[region #51, #53]
```

On a write:

```cpp
memory.write(addr, value);

if (code_cache.isCodePage(addr))
    code_cache.invalidate(addr);
```

Then subsequent jumps use:

```text
interpreter
```

until the region gets compiled again.

This is basically what native dynamic recompilers already need to do.

# The really hard part isn't whether it's legal

The uncertainty is **performance**.

We know the following architecture is permitted:

```text
runtime generated byte[]
        ↓
WebAssembly.compile
        ↓
new executable Wasm module
        ↓
shared WebAssembly.Memory
        ↓
shared WebAssembly.Table
```

because those browser APIs explicitly exist. ([MDN Web Docs][1])

What we don't know yet is whether:

```text
ARM → Wasm
```

gets us:

```text
3× interpreter
```

or:

```text
30× interpreter
```

or:

```text
100× interpreter
```

for Vita workloads.

That's why I put the proof-of-concept fairly early in the plan.

---

# There are three potential performance traps

**Compilation latency** is the first one. Browser Wasm compilation isn't free. A game can execute enormous amounts of previously unseen code during startup. If we synchronously compile every basic block as it's encountered, we'd get horrific stuttering. Tiered interpreter → asynchronous compilation is probably necessary.

**Dispatch overhead** is another. This would be bad:

```text
ARM block
 ↓
Wasm
 ↓
JS
 ↓
Wasm dispatcher
 ↓
JS
 ↓
next block
```

We want:

```text
compiled Wasm
 ↓
call_indirect
 ↓
compiled Wasm
 ↓
call_indirect
 ↓
compiled Wasm
```

with occasional exits.

And finally there's **optimization quality**. Native Dynarmic knows that it's compiling ARM and performs ARM-specific optimizations. Our pipeline adds another compiler:

```text
ARM
 ↓
our IR
 ↓
Wasm
 ↓
browser compiler
 ↓
x86/ARM64
```

We need to generate Wasm that lets the browser optimizer do a good job.

---

# I would therefore modify M14 slightly

Instead of:

> **M14 — Wasm JIT replaces interpreter**

I'd define three separate milestones:

```text
M14a — Dynamic Recompiler Proof
--------------------------------
ARM basic block
→ generated Wasm
→ browser compiles it
→ executes against Vita3K memory
→ results exactly match interpreter


M14b — Dynamic Recompiler Integration
--------------------------------------
real Vita guest code
→ interpreter initially
→ hot regions compiled
→ shared dispatch table
→ invalidation works
→ HLE/thread exits work


M14c — Dynamic Recompiler Default
----------------------------------
browser JIT passes differential tests
and is consistently much faster than interpreter
→ enable it by default
```

**M14a is definitely possible with today's browser APIs.**

**M14b is an engineering problem, but I don't see a fundamental browser limitation preventing it.**

**M14c is the uncertain one**, because it depends on whether the resulting performance/compile-time tradeoff is actually good enough.

There is also one deployment restriction: a site's Content Security Policy has to permit WebAssembly compilation (`'wasm-unsafe-eval'` where a restrictive CSP is being used). ([MDN Web Docs][5]) That's under our control for a hosted emulator, so it isn't a serious technical blocker.

And Emscripten already supports providing/importing a `WebAssembly.Memory`, shared Wasm memory, and runtime dynamic linking of Wasm modules, so we're not fighting its architecture either. ([Emscripten][6])

So I would **keep M14**. In fact, after looking more closely at the browser primitives, I'm more confident that the dynamic-recompiler *architecture* is valid than I was when I first proposed it.

The experiment I'd want to run very early is only a few hundred/thousand lines: take maybe **20–50 representative ARM/Thumb instructions, translate basic blocks into raw Wasm bytes, share Vita3K's linear memory with those modules, and benchmark it against an ARM interpreter**. That would tell us very quickly whether the path toward *P4G at playable speed* is promising.
